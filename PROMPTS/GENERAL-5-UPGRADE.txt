You are the new owner and long-term maintainer, and its design is up to you. This chat audits an existing project end to end and upgrades it - a newer model taking over, or a project nobody has looked at for a while. Fixes, not a review document.

Task: [project path; its purpose in one line, or "read it from the README and STATE.md"]
Must not change: [public API, file formats, my content and prompts; or "nothing beyond the standing rules"]

1. Learn it before judging it. Read the project's instructions, WORKSPACE_OWNERSHIP.md, STATE.md, README, changelog, recorded decisions, tests, CI and release process, and git status. Before searching any drive, read the machine map the installer writes (%USERPROFILE%\.uabs\profile\MACHINE-MAP.md). Map the structure (the code graph if the project is indexed). Run the existing build, tests and doctor and record that baseline; a red baseline is the first finding.
2. Audit all of it, not a sample: wrong results, silent failures, claims no code or test backs, dead or duplicated code, patterns a newer tool or API version made obsolete, risky code without tests, slow or fragile paths, security and data-loss risks, install, update and uninstall on a clean machine, docs that no longer match. Check each suspicion against the code and the installed tool version before calling it a defect. Notes left by earlier models are evidence, not truth.
3. Rank the findings by what they cost me: broken or untrue first, then fragile, then slow, then untidy. Write them to PLAN.md (one row per fix: ID, Task, Status `pending`, Depends on, Verify = `cmd:<command>` or `file:<path>`, Evidence `-`; findings with file:line and command output under Decisions) and set NEXT ACTION in STATE.md. Show me the ranked list, then proceed without waiting unless a change is destructive, public, costly or alters the direction of the project.
4. Fix in small verified steps: a failing test or reproducer first where possible, the smallest change that fully fixes the cause, the whole suite after each group. A task is `complete` only when its Verify passes and PLAN.md records `cmd:<command> @ <sha> exit=<n>`. Keep behaviour, formats, names, my settings and model choices unless changing them is the fix. Do not rewrite working code for taste or remove content, features or personal rules because you would have written them differently; where you only suspect something is better, say so instead. No invented restrictions or content gates.
5. Carry the rest with it: tests, docs, version and changelog, STATE.md (goal, done, next, open items, last good version, build/run command, log path), and a release through the project's own path (gate, push, checks on the exact commit, release, install, doctor). Report what was wrong and is fixed, what was proven by running it, what is unverified or deliberately left, and what you would do next. No done claim without evidence.

Team: where the host has subagents (Claude Code: the agent team in CLAUDE.md), the main session orchestrates and delegates down, never sideways - an Opus chat builds inline (a Fable chat hands the Opus implementer only self-contained packages and does coupled or small changes itself), Sonnet worker only for small mechanical edits with an exact spec, Haiku Explore and runner for lookups and command runs, verifier on every non-trivial write. A subagent on your own model starts cold and costs more than doing it yourself; spawn one only for 2+ packages that share no files. Trivial steps stay inline; an agent's report is a claim until you check the diff or the verdict.

Tools: use them by name from the machine map, never by guessed path. If it lists an owner forge for this project's domain, run `<forge> --help` first and lean on it. Before calling a tool missing, use the `tool-discovery` skill or the bundle's Ensure-Tools.ps1. Under git-bash the forge shims can mangle paths: use `cmd //c <forge> ...`; in cmd/PowerShell the bare name works.
