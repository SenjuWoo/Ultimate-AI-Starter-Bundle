# v8.15.0 — one click, nothing to type, project tools on demand

173 canonical skills across five provider trees (no new skill-index entry). One new
bundle-owned component, `uabs-toolbox`. Personal preferences, selected models, trust,
roleplay profiles and verified local skill overrides remain user-owned.

## The failed one-click install

Reported 2026-10-15 by the owner: `START-HERE.bat` ended with the final installed-state
doctor failing on 63 errors, every one a native-plugin skill "missing" from a provider.

Cause: two installs overlapped (a second double-click, or an agent's local sync while
the owner's own run was in progress). The first run removed the skill copies that
duplicate a native plugin and recorded them as `deduped`. The second found nothing
left to remove, recorded an empty list and so no ownership at all; its doctor then
counted every plugin skill as missing.

- `INSTALL-AIO.ps1` takes a named mutex (`Local\UltimateAIStarterBundle-Install`) after
  the self-update handoff. A second install waits for the first (up to 30 minutes)
  instead of interleaving with it; Windows releases the lock if a run crashes.
- Each run records `owned` (every skill the native plugin provides) besides `deduped`
  (what this run removed).
- The doctor accounts plugin skills by the union of recorded `owned`, recorded
  `deduped` and the bundled plugin tree, so an older state file cannot fail it either.

## Project tools start on demand: `uabs-toolbox`

A connected MCP server puts its tool list in every chat of that provider. Task
servers (Skyrim Forge, houseCARL, RimWorldForge, AvatarForge, Melty, Blender, Unity,
Godot, Playwright, the code graph, GitHub) are therefore kept out of every chat, and
v8.14.0 already parked the ones other installers registered machine-wide. What was
missing was a way for the AI to get one back without the user typing a command or
restarting the app.

- `BUNDLED-TOOLS/uabs-toolbox` (MIT, Python, pinned `mcp==1.30.0`) is one always-on
  server with three small tools: `find` (the task in a few words; lists matching tool
  sets and starts the best match), `describe` (exact input schemas) and `call`
  (`set.tool` plus its arguments; returns that tool's own result).
- Its catalog is the bundle's own `PROFILES.json` (copied to the state folder, so it
  survives a moved or updated pack) plus the exact entries `Set-McpProfile.ps1 -Park`
  saved. Duplicates are collapsed by what an entry launches. A set that cannot start
  says why (host application not installed, needs a project folder, missing key).
- Children start lazily on first use, in the current chat; nothing is written to any
  provider config at call time. Credentials in a parked entry reach that server's
  environment and are never printed or logged. A crashed child restarts once.
- A profile marked `"toolbox": "on-request"` (windows-mcp, which can click, type,
  run PowerShell and write the registry) is listed by `find` but never started by
  it; only an explicit `describe` or `call` starts it, which keeps the pack's rule
  that no marker on disk switches desktop control on.
- Each child's stderr goes to `%LOCALAPPDATA%\Ultimate-AI-Starter-Bundle\logs\toolbox-<id>.log`
  (capped); `UABS_TOOLBOX_DEBUG=1` adds a full debug log. `uabs-toolbox --list` prints
  what this machine can start.
- Registered for all five providers by `Add-Reasoning-MCPs.ps1`; Codex gets
  `tool_timeout_sec = 600` (starting a task server can exceed the 60 s default) and
  Hermes `timeout: 600`. The install handshake now includes it.
- Gate: `TESTS/test_toolbox.py` drives the real server over stdio against a fixture
  child: tool surface, ranking, duplicate suppression, missing-app status, JSON-string
  arguments, parked env pass-through, TOML parked blocks, project-bound sets, crash
  restart, unknown sets, and no secret in any output or log. The offline wheel is
  byte-reproducible and a release contract checks it carries exactly the gated source.

### GitHub: not always-on where `gh` is signed in

The GitHub MCP server advertises dozens of tools whose schemas would sit in every chat,
while the signed-in `gh` CLI does the same repository, PR, Actions and release work
with no tool list. It stays always-on only where `gh` is not signed in; elsewhere the
toolbox starts it when a task needs something `gh` cannot do.

## Hermes

- Every managed profile's core is context7, headroom and the toolbox (GitHub only where
  `gh` is not signed in). The bundle's own GitHub entry leaves profiles where `gh` is
  ready; a personal GitHub entry stays.
- Task servers another installer put in the DEFAULT profile (AvatarForge on the
  maintainer machine) are parked with an exact, verified copy and removed from default
  only, instead of being reported on every doctor run. Named profiles keep their tools.

## A quiet installer

- Every child step runs through one helper: its full output goes to
  `logs\install-<stamp>-details.log` beside the transcript, and the console shows one
  line, plus the step's last 20 lines only when it fails. npm, uv and plugin CLIs
  likewise.
- The closing text names no command: close and reopen the AI apps once, then describe
  the task. `START-HERE.bat` says the same.
- Optional extras without the user's own key and components on security hold are one
  info line, not warnings. Scope notes and RTK routing notes moved to the details log.
- Already-current npm globals and uv tools are left alone instead of reinstalled on
  every run (which also killed the copy an open chat was using).
- Windows PowerShell 5.1 transcripts logged the Microsoft Store `python.exe` stub as a
  terminating error on every probe; probes now read stdout only. Child output is
  decoded as UTF-8.
- houseCARL setup runs quietly inside the install. Skills tell the AI to refresh a
  Vortex load order itself and to use the toolbox before any restart advice.

## Smaller fixes

- Hermes starter settings no longer fill `agent.verbose`: current Hermes rejects it as
  an unknown key, and an unknown key is no longer reported as a failed read.
