# v8.7.38 — fix GitHub alerts on the repository you just wrote

## Any install, any repository

v8.7.37 queried flags and stopped at a report when the alert sat outside the
files that one push touched. It also recorded one repository's code-quality
404 inside the instructions every install would copy.

The wired preamble is what Claude, Codex, Grok, Hermes, and Kimi cache. It
now requires the same automatic step as CI and prompt-cache discipline. After
an agent creates a GitHub repository, pushes, or updates dependencies, it
queries that repository's open Dependabot, code-scanning, and secret-scanning
alerts, fixes the cause, pushes the fix, waits for the new SHA's checks, and
queries again. The work is not done while an alert that change opened is
still open.

`TOOLS/Get-GitHubFlags.ps1` remains the probe when that file is in the
checkout. Any other checkout uses `gh api` on the same open-alert endpoints.
A failed query is unknown, not zero. An alert is not dismissed. A secret is
not printed. A 403 or 404 on code quality means that scan is unavailable on
that repository and stays off. Validity checks, non-provider secret patterns,
OSV-Scanner, Gitleaks, and zizmor stay off.

172 canonical skills. No new MCP server. No dependency pin change.
